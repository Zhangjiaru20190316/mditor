### 三个大坑（都花了不止一轮才定位）
1. **f-string 拼接丢转义**：`f"..." + "\n      }}"` 尾段失去 f 前缀，`}}` 不再转义 → 每个 @keyframes 多一个 `}` → Chromium 丢弃后续整个样式表 → getAnimations 只剩 1 个。教训：拼接字符串里的字面花括号要逐段确认 f 前缀。
2. **animation-delay 方向搞反**：共享 keyframes（0% 隐藏→0.034% 可见）+ **负**延迟 = 进度从 `t+D` 起，永远越过显形点 → 所有字符开场即全可见（像素断言里「L1 全亮但光标在半程」才识破）。正确做法：**正延迟 + `both` 回填**（延迟期取首帧 opacity:0）。循环回卷时字符自然隐藏重打，行为正确。
3. **WAAPI seek 静默失效的表象**：seek 失效其实是坑 1 的 CSS 全灭（动画对象都没建出来），不是 captureScreenshot 缓存。排除法：先 probe computed style（evaluate 里 getComputedStyle），再怀疑渲染缓存。

## 09-08 追加：mp4 糊 → 1440p60 重出

用户反馈「mp4 为什么这么糊」。像素级取证结论：
- **根因是 720p 被放大观看**（1× 直渲源帧 + 610kbps），编码本身在文字区只损失 1%；拉普拉斯方差高≠清晰（锯齿高频会虚增该指标），超采样降回同尺寸后方差略降是 AA 的正常表现。
- **修复**：`cdp_capture.mjs --scale 2`（Emulation.setDeviceMetricsOverride deviceScaleFactor=2 → 截图直接 2560×1440）→ 原生 1440p60 编码（crf16 `-tune animation -x264-params aq-mode=3:aq-strength=0.7`）。成片 vs 源帧保真 98.7%。mditor-promo.mp4（5.7MB）即 1440p 版；frames/ 8 张封面同步换 2K。
- **ffmpeg 9 长跑 PNG→x264 1440p 会累积内存膨胀**（vf Cannot allocate memory；120 帧正常、1800 帧失败，与 preset 无关、ffmpeg 确认 x64、系统 5.8GB 空闲）。解法：4×7.5s 分段编码 + concat demuxer 无损拼 + 重混流。另注意 `-start_number` 从 1 开始会静默丢第 0 帧（分段要 0/450/900/1350）。
- B 站上传选「高清 1440p」档。C 盘余量紧张（1.5GB）是系统 pagefile 占用，重启回收。
