## DR-001 界面语言保持中文单语，暂不引入 i18n 框架

| 项 | 值 |
| --- | --- |
| 编号 | DR-001 |
| 日期 | 2026-09-21 |
| 状态 | 已采纳 |
| 来源 | [`optimization_report4.md`](./optimization_report4.md) §5.2 Q5（第九轮审计，2026-09-20） |

### 背景

全部界面文案为中文硬编码：SettingsModal 约 253 行含 CJK 字面量，App.tsx 确认弹窗、状态栏提示等遍布；仓库无任何 i18n 设施（react-intl / i18next 零匹配）。历轮审计多次注意到这一「缺失」，但它是产品定位问题而非代码缺陷——缺的不是实现，是一次显式决策。

### 决策

1. **界面语言保持中文单语**，不引入 i18n 框架，也不为「将来可能多语言」预留字符串抽取层。
2. i18n 若要启动，**最早排在 App.tsx 拆分（report4 Q2 / M1）与 useMilkdown 拆分（Q3 / M2）两大重构完成之后**；届时若仍无出海计划（如 AppGallery 海外区上架），则永久搁置，不做预投入。

### 理由

- **冲突面：** 拆分前抽字符串等于在 3,232 行的 App.tsx 与 2,703 行的 useMilkdown 上再叠一层全文件级改动，与两大拆分互相制造大规模 merge 冲突面。
- **成本曲线：** 拆分完成后组件/hook 边界清晰，字符串可按组件分批抽取，启动成本约为当前的 1/3（report4 Q5 估计）。
- **需求侧：** 当前无海外分发承诺；为不存在的需求持续付出 key 治理与翻译同步成本不划算。

### 影响

- 后续各轮审计**不再重复提出**「i18n 缺失」类发现（本条即 Q5 建议的「明确记录该决策」）。
- 若未来出现出海计划，重启路径：先完成两大拆分 → 新开 DR 记录推翻本条 → 按组件分批抽取字符串。
- 本决策只约束 UI 文案，不约束面向开发者的内容（docs/ 文档语言、错误码、日志）。
